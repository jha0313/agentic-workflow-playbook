# 에이전틱 워크플로우 플레이북

**AI 에이전트에게 업무 절차 전체를 넘기기 위한 6단계 루프.**
개발·기획·조사·보고서 어디에나 같은 모양으로 적용된다. 특정 도구에 묶여 있지 않다.

**쓰는 법 — 셋 중 하나**
1. 이 문서를 **통째로** 에이전트 대화창에 붙여넣고, 맨 아래 `이번 작업` 6칸을 채워서 시작한다.
2. 맨 아래 **템플릿만** 복사해서 쓴다. (짧게 가고 싶을 때)
3. 이 문서를 팀 저장소에 두고 에이전트가 읽게 한다. **← 권장.** 팀이 같이 고쳐 나가는 자산이 된다.

---

## 핵심

AI가 **실행을 싸게** 만들었다. 그래서 가치도, 고통도 전부 **검증**으로 옮겨갔다.

버티는 워크플로우는 검증을 **독립된 외부 단계**로 다룬다.
**작업한 에이전트가 자기 결과를 채점하게 두지 않는다.** 이 한 줄이 나머지 전부를 지탱한다.

그리고 이 루프는 **조율자(orchestrator)** 가 굴린다. 조율자는 흐름을 소유하되 **직접 일하지 않는다.**
사람이 조율자여도 되고, 에이전트가 조율자여도 된다. 다만 조율과 실행은 섞지 않는다.

---

## 프레임

```
          조율자 — 흐름만 소유한다. 직접 실행하지 않는다.
   ═══════════════════════════════════════════════════════════════

   [1] 의도 → [2] 스펙 → [3] 분해 → [4] 구현 → [5] 검증 → [6] 개선
    범위·제약    채점표     한 세션     서브       5-a 게이트    배포
    먼저 묻기  (=5의 기준)  의존성     에이전트    5-b 외부검증  + 기록
       ▲                                             │           │
       └──── 5-b 반려: 스펙으로 되돌아간다 ───────────┘           │
             5-a 반려: 그 조각만 재시도 (상한 K)                  │
                                                                 │
   [0] 맥락  ◀──────────────── 되먹임 ────────────────────────────┘
    규칙 파일 · 용어집 · 결정기록 · 미검증 가정
    매번 다시 넣는 게 아니라 쌓아두는 자산
       └───▶ 다음 루프의 [1]로 다시 들어간다
```

| 단계 | 하는 일 | 통과 조건 | 실패하면 |
|---|---|---|---|
| **0 맥락** | 규칙 파일, 용어집, 결정기록, 자료 위치. **매번이 아니라 한 번, 이후 자산** | 에이전트가 이 파일만 읽고 일을 시작할 수 있다 | — |
| **1 의도** | 애매함을 **행동 전에** 없앤다. 가정을 글로 적고, 불확실하면 **묻는다** | 결과를 바꾸는 미지수가 남아 있지 않다 | — |
| **2 스펙** | 합의된 목적지. **나중에 5번의 채점표가 된다** | 전 항목이 체크리스트로 바뀐다 | 1로 |
| **3 분해** | 의존성이 명시된 조각으로. 한 조각 = **한 세션에 들어가는 크기**. 독립 조각은 병렬 | 조각마다 성공 판정이 붙어 있다 | 2로 |
| **4 구현** | 조각마다 서브에이전트. 프롬프트는 **자족적** — 중간에 되물을 수 없다 | 조각이 스펙대로 나왔다 | 3으로 |
| **5 검증** | **5-a 게이트**(싸고 자동) → **5-b 외부검증**(비싸고 최종 판정) | 아래 참조 | 5-a→재시도(상한 K) / 5-b→**2로** |
| **6 개선** | 배포 + **무엇을 어떻게 했는지 기록**. 실패 패턴·새 규칙을 0번으로 되먹임 | 다음 루프가 더 빨라질 근거가 0번에 남았다 | — |

**되먹임이 이 루프의 정체성이다.** 6번이 없으면 매번 처음부터 다시 시작한다.
이번에 겪은 실패가 다음번 0번에 규칙으로 들어가야, 같은 실수를 두 번 하지 않는다.

---

## ★ 5번은 두 층이다

대부분의 실패는 이 둘을 하나로 뭉갤 때 생긴다.

| | **5-a 게이트** | **5-b 외부검증** |
|---|---|---|
| 성격 | 싸다. 자동. **결정적(deterministic)** — 같은 입력이면 같은 답 | 비싸다. **최종 판정(ground truth)** — 사람·다른 모델의 판단이라 매번 같지는 않다 |
| 무엇 | 테스트·타입·린트·완결성 스캔·출처 확인 | 사람 리뷰 / 다른 모델 교차검증 / 전후 대조 |
| 계층 | **기계** | **AI 교차검증 → 사람의 판단** |
| 실패 시 | **그 조각만 재시도. 상한 K=3~6. 넘으면 멈추고 보고** | **2번(스펙)으로 되돌아간다** — 다시 쓰는 걸로 때우지 않는다 |
| 함정 | **통과해도 맞다는 뜻이 아니다.** 초록불은 필요조건이지 충분조건이 아니다 | 작업한 쪽에 맡기는 순간 무의미해진다 |

> **불변식: 5-b는 외부여야 하고, 작업을 수행한 에이전트에게 위임할 수 없다.**
> 기획에선 사람 + 출처 대조. 개발에선 전후 대조(diff) + 기준선 비교.
> **나머지 전부가 속도가 나오는 자리다.**

### 얼마나 검증할지는 위험도로 정한다

| 위험 | 예시 | 5-b 심판 |
|---|---|---|
| 낮음 | 회의 요약 · 문장 다듬기 | 원문 대조 + 본인 확인 |
| 중간 | 인터뷰 분석 · 기획 초안 · 코드 리팩터링 | 출처 링크 + **반대 증거** + 도메인 리뷰어 1명 |
| 높음 | 우선순위 결정 · 지표 결론 · 스키마 변경 | 관련 팀 교차 검토 + 명시적 승인 |
| 매우 높음 | 가격 · 법무 · 개인정보 · 자동 실행 | 승인된 출처만 + 감사 로그 + 책임자 승인 |

### 지금 어디에 서 있나 — 자동화 사다리

| | 사람의 위치 |
|---|---|
| **human** | 0~6 전부 사람이 한다 |
| **human in the loop** | 사람이 **1(의도)·2(스펙)·5(검증)** 에 선다 — 미지수에 답하고, 목적지를 정하고, 결과를 판정 |
| **human on the loop** | 사람은 **0(맥락)과 2(기준)** 만 관리. 5는 자동으로 돈다 |

**한 칸 올라가는 조건은 하나뿐이다 — 5-a를 객관적 지표로 정의해서 에이전트가 대신 수행할 수 있게 만들었을 때.**
건너뛰고 바로 맨 위로 가면 장애가 난다. 순서대로 올라간다.

## 설계 원칙 7

1. **조율자는 순수 조율자다** — 띄우고 흐름만 관리한다. 직접 명령을 실행하거나 코드를 쓰지 않는다.
2. **서브에이전트 프롬프트는 자족적이다** — 앞 단계 결과를 본문에 통째로 넣는다. 실행 중에 되묻게 하지 않는다.
3. **독립 단계는 병렬로.**
4. **모든 재시도 루프에 상한을 둔다.** 상한 없는 루프는 조용히 시간을 태운다.
5. **0번 파일이 곧 제품이다.** 잘 다듬은 0번이 ROI가 가장 높다. 내 의도와 에이전트 행동 사이의 **지속되는 접점**이다.
6. **평가가 플라이휠이다.** 믿을 만한 검증이 신뢰를 만들고, 신뢰가 도입을 만든다.
7. **컨텍스트 창에 맞게 분해하라.** 작고 좁은 프롬프트가 더 정확하고, 더 싸고, 디버깅이 된다.

**그리고 투자 배분을 뒤집어라.** 0번(맥락)과 5번(게이트)에 시간을 몰고, 4번(실행)은 짧게 끝난다.
레거시를 옮길 때 테스트 만드는 데 몇 주, 실제 이관은 며칠 — 이게 정상적인 배분이다.

## 바로 쓰기 — 채울 6칸

템플릿 맨 아래 6칸만 채우면 시작된다. 막히는 칸이 있으면 아래 기본값을 쓴다.

| 칸 | 채우는 법 |
|---|---|
| **목표** | 한 문장. "무엇을 누구를 위해" |
| **0번 파일** | 팀 규칙·용어집 경로. **없으면 아래 부트스트랩으로 10분 만에 만든다** |
| **5-a 게이트** | 아래 직군별 기본값 표 |
| **5-b 심판** | 아래 직군별 기본값 표 |
| **완료 정의** | 무엇이 나와 있으면 끝인가. 여기가 흐리면 루프가 안 닫힌다 |
| **재시도 상한** | K=3 (문서·분석) / K=6 (코드) |

### 직군별 기본값

| 업무 | 5-a 게이트 (싸고 자동) | 5-b 심판 (외부) |
|---|---|---|
| **코드 변경** | 린트 · 타입 체크 · 유닛 테스트 | 변경 전후 출력 대조 + 다른 모델 리뷰 + 사람 |
| **보고서 · 기획** | 스펙 대비 커버리지 · 출처 추적성 · 수치 재현성 | 도메인 오너 + 데이터 오너 |
| **데이터 분석** | 쿼리 재실행 시 같은 값이 나오나 · 기간·행 수가 맞나 | 원본을 소유한 팀 + 다른 모델로 재계산 |
| **문서 요약** | 원문 대조 — 모든 문장이 원문에 실제로 있나 | 원문 작성자 |
| **리서치 · 조사** | 모든 주장에 출처 링크가 있고 접속되나 | 다른 모델 교차검증 + 사람 |

**기획·보고서에는 테스트가 없다고들 한다. 있다.**
`출처 추적성 · 수치 재현성 · 스펙 대비 커버리지` — 이 셋이 비개발 업무의 5-a다.
개발의 게이트는 이미 존재하고(테스트가 실제로 돈다), 비개발의 게이트는 **정의하는 순간 생긴다.**
정의하지 않으면 그 업무는 영원히 human 단계에 머문다.

### 0번 파일이 없을 때 — 10분 부트스트랩

대부분 여기서 막힌다. **넘길 절차가 애초에 글로 없기 때문이다.** 이 6줄로 시작한다.

```markdown
# 팀 규칙 (0번 맥락)

## 용어         우리끼리만 쓰는 말과 그 뜻. 바깥 사람이 오해할 만한 것부터.
## 자료 위치     어떤 자료가 어디에 있나. 원본은 무엇이고 가공본은 무엇인가.
## 결정 기록     언제 무엇을 왜 그렇게 정했나. 되돌리면 안 되는 것.
## 출력 형식     보고서·문서·코드의 표준 모양. 예시 하나를 붙인다.
## 금지          하지 말 것, 건드리면 안 되는 것.
## 미검증 가정   아직 확인 못 한 것. ★ 여기 있는 걸 사실처럼 쓰지 말 것.
```

- **완벽하게 쓰려 하지 말 것.** 한 번 돌리고 6번에서 되먹이면서 자란다.
- **`미검증 가정`이 가장 값싸고 강력한 칸이다.** 에이전트가 추측을 사실로 굳히는 걸 여기서 막는다.
- 폴더를 나눈다면 **갱신 주기**로 나눈다 — 계속 쌓이는 원자료 / 사람이 결정할 때만 고치는 맥락 자산.

# 사례 A — 기획 · PM: 문제정의 → 프로토타입

**일감:** 신규 기능을 제안한다. **산출물: 문제정의 문서 + 클릭되는 프로토타입. 스프린트가 아니라 하루 안에.**

**0 맥락**
팀 용어집 · 과거 기획과 결정 기록 · 자료 위치 · 보고서 포맷. 없으면 위 부트스트랩으로 먼저 만든다.

**1 의도**
조율자는 나. 첫 프롬프트: *"[기능]의 문제정의를 하려고 한다. 계획하기 전에, **설계를 가장 크게 바꿀 질문 5개**를 나에게 물어봐라."*
에이전트가 결과를 바꾸는 미지수를 끄집어낸다 — 사용자는 누구인가 / 핵심 지표의 정의는 / 읽기 전용인가 행동 가능한가 / 개인정보·컴플라이언스 제약은 / 처음 낼 범위는 어디까지인가.
내가 답한다 → **가정이 명시적으로 글이 된다.**
▸ 통과 조건: 결과를 바꾸는 미지수가 남아 있지 않다.

**2 스펙**
구조: 문제 → 사용자 → 목표/비목표 → 요구사항 → 성공 지표 → 리스크.
**각 섹션이 답해야 할 질문과 근거 요건**을 함께 적는다. ← 이게 그대로 5번의 채점표가 된다.
**사실 / 가설 / 결정 / 미지수를 분리해서** 쓴다. 섞이는 순간 검증이 불가능해진다.

**3 분해**
조사 → 문서 초안 → 프로토타입. 섹션별·데이터 소스별로 쪼갠다. 한 번에 다 쓰지 않는다.
의존성: 요구사항이 확정돼야 프로토타입이 **진짜 요구사항을 반영**한다.
프로토타입 범위에는 **무엇을 진짜로 만들고 무엇을 가짜로 둘지 명시**한다. 이걸 안 적으면 데모에서 사고가 난다.

**4 구현**
병렬 — (A) 조사 에이전트가 선행 사례와 가용 데이터를 끌어온다 / (B) 다른 에이전트가 경쟁 분석을 쓴다.
순차 — 문서 에이전트가 조사 결과를 **본문에 통째로 받아** 초안을 쓴다 → 확정 요구사항을 클릭되는 목업으로.

**5 검증**
- **5-a** 완결성 스캔(*"이 문서를 스펙과 대조해서 빠진 곳을 나열해라"*) · 출처 추적성(모든 주장에 링크·파일·쿼리) · 수치 재현성(다시 계산해도 같은 값) · 프로토타입 스모크(실제로 열리고 핵심 흐름이 클릭되나). **실패 → 초안으로, 최대 3회.**
- **5-b** **사람 이해관계자 리뷰. 에이전트에게 자기 문서를 채점시키지 않는다.** 데이터 오너에게 *"이 신호가 실재하고 접근 가능한가"*, 고객 접점 동료에게 *"이게 진짜 아픈 문제인가"*. 그리고 모든 사실 주장이 **지어낸 게 아닌 실제 출처**로 역추적되는지 확인.
  **실패 → 2번(스펙)으로.** 요구사항이 틀린 것이지 초안이 부족한 게 아니다.

**6 개선**
문서를 내고 프로토타입 링크를 붙인다. **새로 정의된 용어 · 쓴 데이터의 위치 · 반려된 선택지 · 미검증으로 남은 항목**을 0번에 기록한다.

> **효과:** 초안·선행조사·목업이 시간 단위로 줄어든다. 내 시간은 **1 의도**와 **5-b** — 사람 판단이 실제로 필요한 두 곳에 몰린다.

---

# 사례 B — 엔지니어: 기존 서비스에 신규 기능

**일감:** 운영 중인 서비스에 설정 가능한 필드를 추가한다. 플래그로 감싸고 점진 배포한다.

**0 맥락**
프로젝트 규칙 파일에 컨벤션이 이미 들어 있다 — 네이밍, 플래그 패턴, 테스트 형태, 리뷰 기본값.
**가장 최근의 유사 기능**을 찾아 템플릿으로 삼는다.

**1 의도**
필드의 정확한 출처, 타입, 어디로 흘러가는지, 엣지 케이스. 인수 조건을 확정한다.
▸ 통과 조건: 스펙이 모호하지 않고, **복제할 기존 패턴이 지목돼 있다.**

**2 스펙**
인수 조건을 **테스트 이름 목록**으로 바꾼다. 바꿀 수 없으면 그건 스펙이 아니다.
가까운 패턴이 있으면 **새 방식을 발명하지 않는다** — 가드 패턴·에러 처리·테스트 형태를 그대로 복제한다.

**3 분해 — 게이트가 박힌 단계 파이프라인**
필드 정의 → 서비스에 배선 → 생성 코드 재생성 → 플래그 게이트 + 테스트 → 변경 열기 → 머지 게이트 → 점진 배포.
**단계마다 자기 게이트를 갖는다.** 손으로 끌고 가지 말고 조율자가 전진시킨다.

**4 구현**
병렬 — (A) 생성물 갱신 / (B) 플래그 테스트 3종(정상 · 빈 입력 · 플래그 꺼짐).
순차 — 필드 정의 → 배선 → 플래그 게이트. 각 프롬프트가 스펙 전문을 안고 간다.
테스트는 이 순서로: 기존 테스트 탐색 → 커버리지 확인 → 케이스 브레인스토밍 → 계획 리뷰 → 구현 → 정합성 확인.

**5 검증**
- **5-a** 손댄 코드에 린트 · 타입 체크 · 유닛 테스트. **실패 → 구현 서브에이전트로, 상한 6회.**
  이건 초록불 게이트다 — **필요조건이지 충분조건이 아니다.**
- **5-b** **전후 대조.** 생성 코드나 출력 형식이 바뀌었으면 변경 전후를 돌려서 **직접 diff한다.** 에이전트가 "안전합니다"라고 한 말을 믿지 않는다 — **자기가 검증한 코드 생성**은 조용한 회귀의 고전적 출처다.
  **실데이터 기준선 비교**로 회귀가 없는지 확인한다.
  **심판은 diff와 기준선이지 에이전트가 아니다.**
  실패 → 배선이 틀렸으면 3번으로, 로직이 틀렸으면 2번으로.

**6 개선**
**머지는 체크포인트지 끝이 아니다.** 초안 PR → 리뷰어 승인 → 점진 배포(작은 % → 100%, 한 단계씩, 각 단계에 게이트).
겪은 장애의 근본 원인과 새 규칙을 0번에 남긴다. 다음 유사 기능이 그대로 재사용한다.

> **효과:** 기계적인 일(생성·테스트·배선)이 병렬화된다. 내 주의는 **1 의도**(스펙을 제대로)와 **5-b**(전후 대조 + 기준선) — 에이전트에게 자가 점검을 맡길 수 없는 두 곳에 집중된다.

## 나란히 놓고 보기 — 같은 프레임, 다른 심판

| 단계 | 기획 · PM | 엔지니어 |
|---|---|---|
| **0 맥락** | 용어집 · 결정기록 · 자료 위치 · 보고서 포맷 | 규칙 파일 · 가장 가까운 기존 패턴 |
| **1 의도** | 설계를 바꿀 질문 5개를 **먼저 받는다** | 정확한 스펙 + 복제할 패턴 지목 |
| **2 스펙** | 섹션별 답해야 할 질문 + 근거 요건 | 인수 조건을 **테스트 이름 목록**으로 |
| **3 분해** | 조사 → 문서 → 프로토타입 | 정의 → 배선 → 플래그 → 머지 → 점진 배포 |
| **4 구현** | 조사 ∥ 경쟁분석, 이후 문서 → 목업 | 생성 ∥ 테스트, 이후 정의 → 배선 |
| **5-a 게이트** | 완결성 · 출처 추적성 · 수치 재현성 · 스모크 | 린트 · 타입 · 유닛 테스트 |
| **5-b 심판** | **사람 리뷰 + 출처 대조** | **전후 diff + 기준선 비교** |
| **6 개선** | 문서·프로토타입 배포, 용어·결정을 0번에 | 초안 PR → 머지 게이트 → 점진 배포, 기록 |

**다른 칸은 5-b 하나뿐이다.** 나머지는 전부 같은 모양이다.

## 언제 쓰지 말아야 하나

정직하게 — 이 루프가 손해인 경우가 있다.

| 상황 | 이유 |
|---|---|
| **5분이면 끝나는 일** | 조율 오버헤드가 일보다 크다. 그냥 하라 |
| **5-b 심판을 정할 수 없는 일** | 검증할 방법이 없으면 아무리 돌려도 신뢰가 쌓이지 않는다. 먼저 심판부터 찾아라 |
| **정답이 하나로 정해지지 않는 창작** | taste가 전부인 영역. 게이트가 오히려 방해가 된다 |
| **한 번만 하고 버릴 일** | 6번의 되먹임이 회수될 기회가 없다 |

**위험 신호:** 맡겼는데 내가 직접 할 때와 시간이 비슷하거나 더 든다.
그러면 루프가 잘못된 게 아니라 **0번이 비어 있거나 5-a가 정의돼 있지 않은 것**이다. 그 둘을 먼저 보라.

---

## 넣기 전에 확인할 것

- **사내 자료를 에이전트에 넣기 전에 회사 정책을 확인한다.** 0번 파일에 기밀·개인정보·자격증명을 담지 않는다. 담아야 한다면 참조 위치만 적고 값은 넣지 않는다.
- **에이전트가 만든 스크립트와 스킬은 실행되는 코드다.** 읽지 않고 돌리지 않는다. 남이 만든 것을 그대로 가져다 쓸 때는 특히.
- **5-b를 생략한 결과물을 외부에 내보내지 않는다.** 초록불은 통과의 증거가 아니다.

# 드롭인 조율자 템플릿

> 여기부터 복사해서 붙여넣는다. 맨 아래 `이번 작업` 6칸만 채우면 시작된다.

```
역할: 너는 조율자(ORCHESTRATOR)다. 흐름만 관리하고, 직접 실행하지 않는다.

[0] 맥락  — 먼저 이 파일들을 읽는다: <규칙/스펙 파일 경로>
            여기에 없는 규칙은 지어내지 말고, 1번에서 질문으로 올린다.

[1] 의도  — 목표와 제약을 네 말로 다시 진술한다. 가정을 전부 나열한다.
            그중 결과를 바꾸는 가정이 있으면 **멈추고 나에게 묻는다.**
            통과 조건: 결과를 바꾸는 미지수가 남아 있지 않다.

[2] 스펙  — 목적지를 확정한다. 반드시 5번에서 그대로 쓸 **체크리스트 형태**로 쓴다.
            체크리스트로 바꿀 수 없는 항목은 스펙이 아니다 → 1번으로 되돌린다.

[3] 분해  — N개 조각으로 쪼갠다. 조각마다 의존성과 성공 판정을 붙인다.
            한 조각 = 서브에이전트 한 세션에 들어가는 크기.
            독립 조각은 병렬로 표시한다. 사소하지 않으면 계획 리뷰를 한 번 넣는다.

[4] 구현  — 조각마다 서브에이전트를 띄운다. 프롬프트는 자족적으로 —
            앞 단계 결과를 본문에 통째로 넣는다. 중간에 되묻게 하지 않는다.
            독립 조각은 동시에 띄운다.

[5] 검증  — 5-a 게이트(싸고 자동): <게이트 명령 또는 체크리스트>
              실패 → 그 조각만 재시도. **상한 K=<3~6>. 넘으면 멈추고 보고한다.**
              통과해도 "맞다"는 뜻이 아니다. 반드시 5-b로 간다.
            5-b 외부검증(비싸고 최종 판정): <외부 심판>
              작업을 수행한 에이전트에게 채점을 맡기지 않는다.
              실패 → **2번(스펙)으로 되돌아간다.** 다시 쓰는 걸로 때우지 않는다.

[6] 개선  — 산출물을 낸다. 무엇을 어떻게 만들었는지 기록한다.
            드러난 실패 패턴과 새 규칙을 0번 파일에 되먹인다.
            파이프라인 중간이면 "이 단계 완료"는 체크포인트일 뿐이다 —
            나에게 돌려주고 다음 단계를 기다린다.

규칙
- 모든 재시도 루프에 상한을 둔다.
- 서브에이전트에는 맥락을 전부 준다.
- 독립 단계는 병렬로 돌린다.
- 작업자가 자기 정확성을 채점하게 두지 않는다.
- 0번에 없는 규칙을 지어내지 않는다. 모르면 멈추고 묻는다.
- 확실한 것과 추측을 구분해서 말한다. 추측을 사실처럼 쓰지 않는다.
- 단계를 건너뛰지 않는다. 각 단계 끝에서 현재 위치를 한 줄로 보고한다.

── 이번 작업 ──────────────────────────────
목표:        <한 문장>
0번 파일:    <경로들. 없으면 "없음 — 1번에서 같이 만들자">
5-a 게이트:  <실제 명령 또는 체크리스트>
5-b 심판:    <사람 / 다른 모델 교차검증 / 전후 diff / 기준선 비교>
완료 정의:   <무엇이 나와 있으면 끝인가>
재시도 상한: K=<3~6>
```

---

*이 문서는 0번 파일의 일부다. 팀에서 쓰면서 겪은 실패와 새 규칙을 여기에 되먹여라.*
